## d.5 nuance resolved

The live docs say the child uses its own permissions configuration; the detailed behavior below is only v2.0.19 code, not a guarantee for current releases. In that tag, the child session copies session rules from the parent if `permissions` is not passed; the evaluator combines agent rules and then session rules, with the last match winning. An effective `deny` is not lifted by `always` and short-circuits before the hook; `permission.evaluate` can only adjust the result if the evaluation reaches the hook. Always inspect the effective policy of the instance.

## Evidence layers

- **Current V2 docs:** facts that appear in the linked pages, including the experimental API label; only the active server's `/openapi.json` is an operational reference.
- **Code observation:** behavior verified only in the `v2.0.19` tag; it does not imply that a later version keeps the same contract.
- **Local inference or convention:** orchestrator/ledger rules are identified as such and not as native states or guarantees.
- **Do not infer:** stable compatibility of experimental HTTP routes, general or per-prompt-message-ID deduplication (the exception is the exact compaction retry with the same ID), maximum concurrency or file locks of the server, current validity of the `all` mode, equivalence between tab and `sessionID`, or complete permission inheritance between parent and child.
